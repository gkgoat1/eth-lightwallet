# Plan: eth-lightwallet 5.1.0 — EIP-1559, v4 keystore format (PQ-hybrid), async internals

- **Status:** Implemented (Phases 1–4 done; Phase 5 docs/types done; release pending)
- **Date:** 2026-10-08 (implemented 2026-10-08)
- **Repo:** `@gkgo/eth-lightwallet` (fork `gkgoat1/eth-lightwallet`), base = v5.0.0 (`8e263dd`, tag `v5.0.0`)
- **Target release:** **5.1.0** — strictly backwards-compatible minor. No existing API removed or changed in behavior; all new capability is additive.
- **Predecessor plan:** `docs/plans/2026-10-08-modernize-ts-tsdown-esm.md` (the 5.0.0 modernization; this builds on its frozen `legacy/` oracle + golden/comparison/e2e harness).

## 1. Goals

Three additive feature sets, all opt-in and non-breaking:

1. **EIP-1559 (type-2) transactions** alongside the existing legacy (type-0) path.
2. **A new `v4` keystore format** with tighter security and modern encryption
   (noble AEAD), **post-quantum for all non-Ethereum asymmetric crypto**, and a
   **migration path v3 → v4** (and v1/v2 → v3 → v4). v3 stays fully supported.
3. **`async` internals** with **both** promise-returning async methods **and**
   callback wrappers for backward compatibility.

## 2. Non-goals / hard constraints

- **No change to v3 behavior or format.** v3 vaults keep loading, decrypting,
  deriving identical addresses/keys, and signing identical legacy txs. All 5.0.0
  goldens + comparison + e2e suites must stay green unchanged.
- **Ethereum asymmetric crypto stays classical.** secp256k1 (addresses, tx
  signatures, ECDSA message signing) is dictated by the EVM and **cannot** be
  post-quantum — a PQ Ethereum signature is not valid on-chain. "Post-quantum"
  applies **only to the non-Ethereum asymmetric layer** (the `encryption`
  module's off-chain message encryption), never to tx/address signing.
- **No new transaction types beyond type-2** (no 2930 access-list, 4844 blob,
  or 7702 in 5.1.0). Type-2 only.
- **No removal of the v1/v2/v3 upgrade paths** or the legacy comparison oracle.
- Callback API is **kept**, not deprecated (wrappers, per §6).

## 3. Compatibility invariants (must not regress)

Pinned by existing suites (unit + golden + comparison + Anvil e2e):

- v3 keystore serialize/deserialize byte-shape and decryption.
- HD derivation (`m/0'/0'/0'` default-agnostic, `hdPathString` required),
  `addrprivkey100` vectors, first-5-address goldens.
- scrypt KDF `logN=14, r=8, p=1, dkLen=32` byte-exact for v3 password→key.
- Legacy tx signing `v = 27/28` (no chainId) / EIP-155 when `chainId` passed;
  `rawSignedTx` goldens byte-exact.
- tweetnacl secretbox/box ciphertext cross-compat (v3 `encryption` module).
- v1/v2 → v3 upgrades byte-exact vs committed fixtures.

Any 5.1.0 change that alters the above is a bug, not a feature.

## 4. Feature 1 — EIP-1559 (type-2) transactions

### Design

Add a parallel, additive path; legacy stays default.

- **`txutils`** (new functions, existing ones untouched):
  - `create1559Tx(txObject)` → `FeeMarket1559Tx` via `createFeeMarket1559Tx`
    (`@ethereumjs/tx@10` — already a dep, confirmed present). Accepts
    `maxFeePerGas`, `maxPriorityFeePerGas`, `gasLimit`, `nonce`, `to`, `value`,
    `data`, `chainId` (**required** for 1559 — EIP-155 replay protection is
    baked into type-2).
  - `functionTx1559(abi, functionName, args, txObject)` and
    `valueTx1559(txObject)` — 1559 analogues of `functionTx`/`valueTx`.
  - `createContractTx1559(fromAddress, txObject)` — deploy; address prediction
    unchanged (CREATE address is sender+nonce regardless of tx type).
- **`signing`**:
  - `sign1559Tx(keystore, pwDerivedKey, rawTx, signingAddress)` → parses with
    `createFeeMarket1559TxFromRLP`, `.sign(privKey)` (confirmed sync in
    `@ethereumjs/tx@10`). Returns unprefixed hex (matches `signTx`).
- **`keystore`**:
  - `signTransaction` gains **opt-in 1559 via an EXPLICIT `txType`**
    (decision, t-9be9 §1): `txType: 2` → build+sign type-2; `txType: 0` /
    omitted → legacy. **No inference from fee fields** — a user setting
    `gasPrice` must never silently produce a type-2 tx (or vice versa), and
    someone passing `maxFeePerGas` for estimation must still get legacy unless
    they opt in. Mixed/contradictory fee fields for the declared type → clear
    error.

### Tests
- Golden: generate type-2 signed-tx vectors from the **frozen oracle cannot**
  (4.0.0 has no 1559) → instead generate with the new code and **self-pin**, plus
  cross-check against an independent producer (viem `signTransaction`) for the
  same (key, tx) → byte-equal.
- Anvil e2e: fund golden address, send a 1559 value transfer + a 1559
  `SimpleStorage.set` call, assert mined with `type: '0x2'` and correct
  effective gas. Anvil supports 1559 natively.

## 5. Feature 2 — v4 keystore format (tighter security + PQ-hybrid encryption)

### 5.1 Threat-model deltas vs v3

| v3 (current) | v4 (target) | Rationale |
|---|---|---|
| scrypt `logN=14, r=8, p=1` password KDF | **Argon2id** (memory-hard, side-channel resistant) — `@noble/hashes/argon2.js` (confirmed present) | Modern KDF guidance; scrypt is fine but Argon2id is the current recommendation |
| tweetnacl `secretbox` (XSalsa20-Poly1305) for seed/keys | **noble AEAD** — XChaCha20-Poly1305 (`@noble/ciphers@2.4.0`) with **AAD** binding ciphertext to vault context | AEAD + associated data prevents ciphertext transplant across vaults/fields |
| No integrity/version binding per field | AAD includes `{format:'lw4', field, version}` | Tamper-evidence |
| `encryption` module: nacl.box (Curve25519 XSalsa20-Poly1305), classical only | **PQ-hybrid**: X25519 **+ ML-KEM-768** (FIPS 203) via `@noble/post-quantum@0.7.1` `hybrid` | Harvest-now-decrypt-later protection for off-chain messages |
| `version: 3` | `version: 4` | explicit format marker |

### 5.2b Argon2id profile (decision, t-9be9 §4)

64 MiB (`m=65536`) is **too heavy for a browser hot-wallet** (mobile Safari /
low-end jank+OOM risk; current scrypt logN=14 ≈ 16 MiB). v4 default is
**`m=32768` (32 MiB), `t=3`, `p=1`**, with a documented **`browser` profile
(`m=16384`–`32768`)** and `m=65536` available for desktop/high-security. The
params are stored in the vault (§5.2), so they're tunable per-vault without
breaking decode.

### 5.2 v4 serialization format (spec)

```jsonc
{
  "version": 4,
  "kdf": {
    "alg": "argon2id",
    "m": 32768,        // KiB memory (32 MiB default — see §5.2b)
    "t": 3,            // iterations
    "p": 1,            // parallelism
    "dkLen": 32,
    "salt": "<base64>" // 16 bytes, CSPRNG
  },
  "hdPathString": "m/0'/0'/0'",
  "hdIndex": 0,
  "encSeed": {                    // AEAD over the 120-char padded seed
    "alg": "xchacha20poly1305",
    "nonce": "<base64 24B>",
    "ct": "<base64>",
    "aad": "lw4:seed:4"           // bound at encrypt time; stored for auditability
  },
  "encHdRootPriv": { "...": "same AEAD envelope, aad=lw4:hdroot:4" },
  "encPrivKeys": {
    "<address-no-0x>": { "alg": "xchacha20poly1305", "nonce": "<base64>", "ct": "<base64>", "aad": "lw4:privkey:<address>:4" }
  },
  "addresses": ["<hex-no-0x>", ...],
  // Off-chain (non-Ethereum) asymmetric encryption public material, PQ-hybrid:
  "pq": {
    "x25519": { "<address>": "<base64 x25519 pub>" },   // classical, from secp256k1 privkey bytes (v3-compatible convention)
    "mlkem768": { "<address>": "<base64 ML-KEM-768 encaps pub>" }
  }
}
```

Field rules:
- `version` MUST be `4`. `kdf.alg` MUST be `argon2id` for v4.
- AEAD `aad` is **required** and verified on decrypt; mismatch → decryption fails.
- `encPrivKeys` keyed by non-prefixed lowercase address, same as v3.
- `pq` is **optional** (populated lazily on first `addressToPublicEncKey`-style
  call for v4) to keep vault creation cheap.

### 5.2a Default write format (decision, t-9be9 §3)

**v3 remains the DEFAULT write format.** `createVault` produces a **v3** vault
unless the caller explicitly opts into v4 (`createVault({..., format: 4})` or a
v4-specific constructor). v4 is strictly opt-in until 5.1.0 is proven —
existing-user vault compatibility must never depend on a brand-new format.

### 5.3 Migration

- `upgrade.upgradeV3ToV4(oldSerialized, password, opts, cb)`:
  1. `deserialize` v3, `keyFromPassword` (scrypt) to unlock.
  2. Re-derive `pwDerivedKey` with **Argon2id** over `{password, new salt}`.
  3. Re-encrypt seed / HD-root / each privkey under AEAD with AAD.
  4. Generate ML-KEM-768 keypairs for each address (fresh CSPRNG; the encaps
     pubkey is stored, the decaps secret is kept encrypted alongside the
     privkey or re-derived — see Open Questions §9.2).
  5. Emit v4 JSON. Old v3 blob is untouched (caller discards).
- `KeyStore.deserialize` auto-detects `version` (3 → v3 path, 4 → v4 path).
  A v4 vault **cannot** be opened by 5.0.0 (it will throw the "old version"
  guard inverted) — acceptable: v4 is new-only.
- v1/v2 → v4 = existing v1/v2 → v3 upgrade, then v3 → v4.

### 5.4 PQ scope (explicit)

- **PQ applies ONLY to the `encryption` module's off-chain asymmetric
  encryption** (`asymEncryptString`/`multiEncryptString` etc.) when operating on
  a v4 vault. This becomes X25519+ML-KEM-768 hybrid (both must be broken to
  recover the message).
- **Ethereum signing/addresses are NOT PQ** (EVM constraint, §2). This is stated
  prominently in docs to avoid a false sense of on-chain PQ safety.
- The v3 `encryption` module (pure nacl.box) is unchanged and stays for
  backward compat; PQ-hybrid is v4-only.

## 6. Feature 3 — async internals + dual (async/callback) API

### Principle
Make the **internal implementation async-first** (promise), and expose **both**:
- async methods returning Promises (new, canonical), and
- **callback wrappers** preserving the 5.0.0 signatures for compat.

### Mapping (keystore, the callback-heavy module)

| 5.0.0 (callback) | 5.1.0 async (new, canonical) | 5.1.0 callback (kept) |
|---|---|---|
| `KeyStore.createVault(opts, cb)` | `KeyStore.createVaultAsync(opts): Promise<KeyStore>` | `createVault(opts, cb)` wraps the async |
| `ks.keyFromPassword(pw, cb)` | `ks.keyFromPasswordAsync(pw): Promise<Uint8Array>` | `keyFromPassword(pw, cb)` wraps |
| `KeyStore.deriveKeyFromPasswordAndSalt(pw, salt, cb)` | `KeyStore.deriveKeyFromPasswordAndSaltAsync(...): Promise<Uint8Array>` | original wraps |
| `ks.signTransaction(txParams, cb)` | `ks.signTransactionAsync(txParams): Promise<string>` | `signTransaction(txParams, cb)` wraps |
| `ks.hasAddress(addr, cb)` | `ks.hasAddressAsync(addr): Promise<boolean>` | `hasAddress(addr, cb)` wraps |
| `upgrade.upgradeOldSerialized(s, pw, cb)` | `upgradeAsync(s, pw): Promise<string>` | original wraps |

- Existing **sync** methods (`generateNewAddress`, `getAddresses`, `getSeed`,
  `exportPrivateKey`, `serialize`, `isSeedValid`, `_encryptString`, …) stay sync.
- `signMsg`/`signMsgHash`/`recoverAddress` are **already async** in 5.0.0
  (return Promises); 5.1.0 **adds callback forms** (`signMsgCb`, or an optional
  trailing callback) for symmetry — see §9 Open Questions.
- Internals: KDF, password provider flow, and encryption all become `async`
  under the hood; the callback wrappers are thin (`fn(...).then(v=>cb(null,v), cb)`).

### Tests
- For every async/callback pair, assert **identical results** from both forms.
- All 5.0.0 callback-driven tests stay green (the wrappers must not change
  behavior, error shapes, or ordering).

## 8. Phases

### Phase 1 — async internals + dual API (no format/crypto change)
- Convert KDF + password-provider flow + keystore async methods; add
  `*Async` canonical methods + callback wrappers.
- Pairwise identical-result tests; 5.0.0 suites stay green.
- **Exit:** async + callback both work; zero behavioral change.

### Phase 2 — EIP-1559
- `txutils`/`signing`/`keystore` 1559 additions (opt-in, legacy default kept).
- Self-pinned goldens + viem cross-check + Anvil e2e (1559 transfer + call).
- **Exit:** 1559 txs sign + mine on Anvil; legacy path untouched & green.

### Phase 3 — v4 format
- `src/v4/` (or `keystore-v4.ts`): Argon2id KDF, AEAD envelopes w/ AAD, v4
  serialize/deserialize, `upgradeV3ToV4`.
- v4 golden fixtures (self-pinned) + round-trip + tamper-evidence tests (AAD
  mismatch fails) + migration tests (v3→v4 produces same addresses/keys).
- **Exit:** v4 vaults create/open/migrate; v3 fully intact.

### Phase 4 — PQ-hybrid encryption (v4 only)
- X25519+ML-KEM-768 hybrid in the `encryption` module for v4 vaults.
- KEM round-trip + hybrid-decrypt-must-have-both tests + interop shape tests.
- **Exit:** v4 off-chain encryption is PQ-hybrid; v3 encryption unchanged.

## 9. Open questions

1. ~~**1559 opt-in:** infer vs explicit~~ → **DECIDED (t-9be9): explicit
   `txType`**, never fee-field inference.
2. **v4 ML-KEM secret storage:** store the ML-KEM decaps secret encrypted next
   to each privkey, or re-derive deterministically? (Leaning: store encrypted —
   deterministic KEM-from-seed is non-standard and riskier.)
3. **Async message-signing callback form:** add `signMsgCb`-style functions, or
   accept an optional trailing callback on the existing async methods? (Leaning:
   optional trailing callback — single method, dual behavior.)
4. ~~**Argon2id params**~~ → **DECIDED (t-9be9): default `m=32768` (32 MiB),
   with a documented `browser` profile (16–32 MiB); 64 MiB not the only
   option.**
5. ~~**v4 as default write format**~~ → **DECIDED (t-9be9): v3 stays default;
   v4 strictly opt-in** until proven.
6. **v4 field naming/encoding** in §5.2 — final review before freezing (the
   format becomes load-bearing once vaults exist in the wild).

## 10. Risks

| Risk | Mitigation |
|---|---|
| PQ lib maturity (@noble/post-quantum 0.x) | pin exact version; goldens pin KEM vectors; document 0.x status |
| Argon2id memory cost in browser | tunable params in format; e2e in jsdom + Anvil; confirm with hot-wallet |
| Dual API surface drift (async vs callback diverge) | pairwise identical-result tests for every pair |
| v4 format frozen too early | §5.2 spec review gate before any v4 vault is produced downstream |
| 1559 changes legacy default accidentally | legacy is default unless 1559 fee fields present; golden + e2e guard |
